# 团队知识库系统：设计原则与 MVP 规划

> 本文档整合了本项目的设计哲学、技术佐证、MVP 架构以及后续演进路线。

---

## 一、设计哲学：从“技术自嗨”到“减法实战”

### 1.1 核心观点
- **90% 的 Agent 记忆方案是“技术自嗨”**，盲目堆砌向量库、知识图谱，导致成本飙升、记忆污染、Debug 灾难。
- **真正实用的系统是做减法**：轻量化、结构化、可审计，覆盖 95% 的实战场景。

### 1.2 三大陷阱与我们的应对

| 陷阱 | 描述 | 我们的应对 |
| :--- | :--- | :--- |
| **成本账** | 存储全量上下文、高频调用模型，ROI 为负。 | 仅存核心四维（目标/方案/结果/痛点）+ 轻量 Markdown 正文，无外部依赖。 |
| **记忆污染** | 向量检索只看语义相似，忽略逻辑正确性；知识图谱过度连线导致注意力稀释。 | 采用 **Tag + 倒排索引** 精准检索，杜绝语义模糊匹配。 |
| **Debug 灾难** | 向量/图谱链路黑盒，无从排查。 | 文件系统即数据库，所有数据可读可编辑，支持 `grep` 和人工直接修改。 |

### 1.3 我们的“清爽记忆方案”
1. **结构化行为回溯备忘录**：提取目标、方案、结果、痛点四个维度。
2. **Tag + 倒排索引精准检索**：使用四维标签（场景/域/类型/甲方）加别名映射，避免向量检索的模糊性。
3. **“Dream模式”（夜间质检）**：定期去重、合并、归档，保持记忆库精简高纯。
4. **人在回路**：Agent 只写草稿，人工审核入库。

## 二、技术佐证与依托

### 2.1 业界共识与社区讨论
- **“90% 团队用错”** 的说法在多个技术社区（如 Memvid 讨论）中得到印证，指出大多数团队过度设计记忆系统。
- **“三大结构性缺陷”** 的提法在 Agent 记忆系统批评文章中反复出现，与我们归纳的陷阱完全吻合。
- **“成本是头吞金兽”** 被广泛认为是大规模部署 Agent 记忆的首要障碍。

### 2.2 学术与工程研究
- **香港中文大学 & 浙江大学**：联合发表论文深入剖析 Agent“记忆”的本质缺陷，强调“记忆污染”与“可扩展性危机”。
- **南洋理工大学 MemSkill**：提倡“偷懒”式核心记忆技能，仅保留关键经验和最佳实践。
- **亚马逊云科技**：系统讨论了 Agent 记忆系统的“工程税”，指出向量检索在实战中的高成本与低回报。

### 2.3 前沿架构的共鸣
#### 与 Andrej Karpathy 的 `LLM-Wiki` 模式高度一致
- **核心思想**：让 AI 增量式构建和维护一个持久化的 Markdown 知识库，而非依赖外部数据库。
- **三层架构**：原始资料 → Wiki 页面 → 模式规范（Schema）。
- **我们的映射**：
  - `原始资料` → 业务文档、聊天记录等输入源（未实现，由前置清洗工具处理）。
  - `Wiki 页面` → `company_knowledge/开发/` 下的 `.yaml` 文件。
  - `模式规范` → `AGENTS.md` 维护手册，指导 AI 如何写入和整理。
- **Dream 模式来源**：`LLM-Wiki` 的维护过程包含 AI 的“沉思（Dreaming）”或“整理（Linting）”环节，与我们的夜间质检一致。

### 2.4 开源项目实践
- **`memora` / `openclaw-memory` / `Memori`**：均支持 **SQL** 和 **Tag 过滤** 进行精确检索，验证了 Tag+结构化查询的可行性。
- **Hindsight / PlugMem / LightMem**：探索结构化、轻量化的记忆方案，强调可审计性和可逆性。

## 三、MVP 架构（已实现部分）

### 3.1 总体架构（分层视图）
```
表示层：Trae IDE / MCP Client / CLI / 人工编辑
服务层：MCP Server (HTTP/JSON-RPC) → /query, /draft
领域层：检索引擎（倒排索引）、标签管理器（别名映射）、文件监视器（热加载）
基础设施层：文件系统（company_knowledge/）
```

### 3.2 目录结构
```
company_knowledge/
├── 开发/
│   ├── 通用规范/
│   ├── 甲方A-XX银行/
│   └── 资产库/
├── drafts/
├── archive/
├── .tag_aliases.yaml
└── AGENTS.md
```

### 3.3 核心模块
- **文件系统读写器**：扫描 `.yaml`，解析 YAML 头 + Markdown 正文，支持热加载。
- **标签管理器**：强制小写+中划线，加载别名映射，验证四维标签完整性。
- **检索引擎**：基于倒排索引（tags + title + aliases + content 前100字），按命中次数排序返回 Top 5。
- **MCP 服务层**：提供 `/query`（检索）和 `/draft`（提交草稿）接口。
- **人工审核辅助**：草稿列表、确认入库、废弃接口。

### 3.4 技术选型
- Go 1.23+ 标准库（`net/http`, `log`, `testing`）
- `gopkg.in/yaml.v3`（唯一外部依赖）
- `github.com/fsnotify/fsnotify`（热加载）

## 四、MVP 未实现但已规划的功能

以下功能已设计，因优先级或复杂度暂未纳入 MVP，将在后续迭代中逐步落地。

| 功能模块 | 描述 | 规划优先级 | 依托技术/参考 |
| :--- | :--- | :--- | :--- |
| **前置文档清洗** | 支持 DOCX/PDF/PPTX 等格式自动转换为 Markdown，提取图片到资产库。 | P1（后续迭代） | MinerU（开源项目） |
| **LLM 自动标签提取** | 由 LLM（如 DeepSeek V4 Pro）从文档内容中自动生成四维标签，减少人工标注。 | P1 | DeepSeek V4 Pro / 豆包 Seed 2.1 Pro |
| **批量存量文档处理** | 一次性处理 100+ 存量文档，自动生成 YAML 草稿，人工审核入库。 | P1 | MinerU + DeepSeek V4 Pro |
| **Dream 模式（自动整理）** | 定时（如每周）扫描重复/相似记录，去重合并，归档旧版本。 | P2 | LLM-Wiki 的“沉思”机制 |
| **多领域扩展** | 支持“运维”、“项目管理”、“客户与商务”等一级目录，与“开发”并列。 | P2 | 设计已预留扩展能力 |
| **标签表自动维护** | 当新标签出现时，自动提示是否加入 `.tag_aliases.yaml`，并统计标签使用频率，辅助人工审查。 | P2 | 标签管理器的基础能力 |
| **检索结果解释** | 返回每条结果时，附上命中的标签和关键词，让用户理解为何命中。 | P3 | 倒排索引自带得分明细 |
| **跨语言检索支持** | 支持中英文混合查询，分词器优化（如引入 `go-icu` 或 `gse`）。 | P3 | 社区分词库 |
| **权限与多用户** | 区分只读、提交草稿、审核入库等角色，适配团队分工。 | P3 | 后续评估是否需要 |
| **Web UI 管理界面** | 提供简单的 Web 界面，方便非技术成员查看、搜索、审核草稿。 | P3 | 可选（Vue/React + Go 嵌入静态文件） |

### 4.1 前置清洗与标签提取的落地路径（待实现）
```
存量文档（PDF/DOCX）→ MinerU（转 Markdown）→ DeepSeek V4 Pro（提取四维标签）→ 生成 YAML 草稿 → 人工审核 → 入库
```

### 4.2 Dream 模式具体设计（待实现）
- **触发**：Cron 定时（如每周日凌晨 2 点）或手动触发。
- **扫描范围**：`开发/` 下所有 `status: active` 的记录。
- **重复判定**：`tags` 交集 > 2 个，且文本相似度（Jaccard / TF-IDF）> 0.6。
- **合并动作**：
  1. 保留 `updated_at` 最新的记录为主记录。
  2. 将旧记录的 `content` 以“历史补充”引用格式追加到主记录末尾。
  3. 将旧记录移动到 `archive/`，`status` 改为 `archived`。
- **孤儿图片清理**：扫描 `资产库/`，若某图片未被任何 YAML 的 `images` 字段或正文引用，则移至 `archive/unused_assets/`。

## 六、总结

本系统以 **“减法”** 为设计哲学，以 **“Tag + 倒排索引”** 为检索核心，以 **“文件系统即数据库”** 为存储基础，以 **“人在回路”** 为质量保障。其设计理念与 `LLM-Wiki`、MemSkill、Hindsight 等前沿思想高度一致，并获得了学术研究与工程实践的佐证。

MVP 已实现核心的检索、草稿提交和人工审核流程，未实现的前置清洗、LLM 标注、Dream 模式等功能均有清晰的落地路径和优先级。整个系统遵循 **“先跑通，再完美”** 的演进策略，确保每一步都产生实际价值。
