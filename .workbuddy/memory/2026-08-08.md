## kb-pilot 技术选型评估（结论：不采用）

评估 waylondev/kb-pilot 是否作为 memory-system 的下一形态，产出 `docs/kb-pilot-evaluation.md`。

**结论：不采用，选择性吸收 3 个设计点。**

关键事实（GitHub API 实测）：
- 仓库 2026-07-31 创建，评估时仅 8 天；10 star / 1 fork / 0 watcher / 0 issue；单人贡献
- 全仓 9 个文件，实际代码仅 2 个 Python 脚本（build_tree.py 是 `^(#{1,6})\s+(.+)$` 标题正则解析器 + build_manifest.py 聚合器），文档 27KB 为代码量 2.4 倍
- 无 LICENSE 文件（API 返回 None，README 声称 MIT）→ 商用有法律瑕疵
- 零测试、零基准

核心批判：
- 宣传称「检索环节 100% 确定」，但其 `kb-chat/SKILL.md` 明写 Step1 文档路由与 Step2 章节定位均为 `semantic matching`（LLM 判断）。确定的只是「已知行号后取文本」，而找位置才是召回失败的真正来源 —— 偷换概念
- manifest.json 需整体入上下文做路由 → 上下文窗口是硬天花板，作者自述「数百文档」是架构真实上限
- 只识别 ATX 标题，文档层级差时树退化为巨大节点且无声降级
- 文中「FinanceBench 98.7%」是 PageIndex 的成绩不是它的；其余数据无可复现脚本

**问题错配（最关键）**：kb-pilot 全部价值建立在「长文档不该被机器切碎」上，而 memory-system 的知识单元是人工撰写的原子 YAML 条目，分块由人在撰写时完成 —— 该痛点本项目从设计上已绕开。且我们的消费方是高频调用的 Agent，用多轮 LLM 路由替换 <5ms 倒排索引，成本涨 1–2 个数量级而收益为零。

方向判断：无向量/树导航方向本身有效（PageIndex、TreeRAG 已验证），但**品类可信度不能转移给具体项目**。未来若真需长文档能力，应作为旁路能力引入并优先选 PageIndex，不要重构现有 MCP 服务。

值得独立吸收的 3 点：
1. 行号级引用 `#L{start}-L{end}`（改 `internal/search` + `internal/server`），提升答案可核验性
2. 为知识条目增加 LLM 生成的 `summary` 字段纳入索引，补充现有纯词法倒排的同义/意图召回（增强而非替换）
3. append-only 纠错闭环（重复即共识、冲突并列），补齐 `drafts/` 只覆盖新增知识的缺口

## 🔴 重大发现：两个未修复的严重缺陷（最高优先级）

从 git 历史挖出首次提交 `f3ca069` 含 `docs/mvp-evaluation.md`（2026-06-28 自评报告），在 `c54a774` 迁移知识库时被连带删除。**已恢复该文件到 docs/。**

报告标注的两个 🔴 问题**经核查至今未修复**：

1. **路径遍历漏洞**（`internal/server/server.go:260` approve / `:289` reject）：`filePath := r.URL.Query().Get("path")` 仅校验非空，无路径约束，直接进 `fs.ParseFile` → `os.ReadFile`/`os.Remove`。构造 `?path=../../../<file>` 可删除服务端任意文件。修复：`filepath.Clean` + `filepath.Rel` 约束在 `drafts/` 内。
2. **score 恒为 0**（`server.go:162`）：`fs.Document.Score float64`（fs.go:26，注释称 "populated by search engine"）**从未被赋值**；引擎实际用 `Result.Score int`（search.go:91）。修复：改读 `r.Score`（语义 lower is better）。

**教训**：自评报告属长期资产，不应随临时性迁移被删。任何架构演进都应排在这两项修复之后。
